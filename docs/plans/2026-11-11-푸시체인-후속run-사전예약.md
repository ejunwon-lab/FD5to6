# 설계 노트 — 텔레그램 푸시 체인 사망 재발 방지 (후속 run 사전 예약)

- 날짜: 2026-11-11 · 대상: `.github/workflows/telegram-push.yml` (CI/스케줄 파이프라인 → `/design-check` 대상)
- 배경: errors.md 2026-11-11 — 5일 새 체인 사망 2회. ①11/7 poke curl 31분 멈춤 → job `timeout-minutes: 130` 초과로 cancelled ②11/11 02:26 KST 러너 유실 → job 45분 뒤 failure. 둘 다 job 끝의 "Dispatch next"(`if: success()`)와 "Alert"(`if: failure()`)가 돌지 않아 체인이 **소리 없이** 끊김.

## 안 변경 (11/11 pending 원안 → 측정 후 수정)

| 원안 | 측정 결과 | 결정 |
|---|---|---|
| curl `--max-time 90` | 11/11(v34, poke마다 가격 갱신) poke 응답 최대 **64초**, p95 45초 (run 5개·113회 실측) | 90초는 여유가 부족해 정상 응답을 끊을 수 있음(→ HTTP=000 → watchdog 비정상 카운트). GAS 실행 상한 6분을 넘는 응답은 없으므로 **`--max-time 400`**(+`--connect-timeout 30`) |
| 알림 조건 `failure() \|\| cancelled()` | 러너 유실 때는 job 안의 어떤 step도 실행되지 않음(11/11) | 조건만 넓혀서는 11/11을 못 막음 → 아래 사전 예약으로 대체 |
| watchdog 장중 "active run 0" 재시드 | watchdog의 장중 실행도 결국 GH cron(best-effort). 11/11 09:00~09:40 cron이 미발화한 그 시계 | 같은 시계를 하나 더 두는 것은 효과가 작음 → **보류**(잔여 위험 R1~R3가 재발하면 독립 시계로) |

**핵심 변경 — 후속 run 사전 예약**: 다음 run을 job **끝**에서 dispatch하던 것을 **시작 5분 뒤**(2번째 poke 직후)에 dispatch한다. `concurrency` 그룹이 이 run을 pending으로 세워 두고, 현재 run이 **어떻게 끝나든**(성공·실패·취소·러너 유실 판정) 곧바로 이어받는다. 체인 생존이 "job이 끝까지 살아 있음"에 더는 의존하지 않는다.

## 1. 외부 동작 가정
- G1 같은 concurrency 그룹(`cancel-in-progress: false`)은 실행 1개 + pending 1개. 새 run이 오면 기존 pending은 취소되고 새 run이 그 자리를 차지 → **사실(이 repo 실측)**: 42839782919(cron, 11/10 14:59Z 생성)가 끝 dispatch 42853334158 생성(16:19:16Z) 2초 뒤 cancelled.
- G2 pending run은 2시간 가까이 기다려도 자동 취소되지 않음 → **사실(실측)**: 42640580479가 11/9 15:02Z~16:59Z(117분) pending으로 있다가 교체로만 취소됨. 42627114291(cron)은 85분 pending 뒤 실행돼 success.
- G3 실행 중 run이 끝나면(결론 무관) pending run이 시작 → 성공 종료 후 이어받음은 실측(위 42627114291). **취소·실패 종료 후 이어받음은 [검증 필요]** → 스모크 S3에서 취소로 확인. 러너 유실은 재현 불가. GitHub이 그 run을 failure로 판정하는 시점(11/11 실측 45분)에 그룹이 비므로 같은 경로로 이어받는다고 판단(추론).
- G4 실행 중인 run 안에서 GITHUB_TOKEN으로 자기 workflow_dispatch 가능 → **사실**: 현행 끝 dispatch가 정확히 이것(6/10 이후 매일 ~12회).
- G5 run의 워크플로 파일은 **생성 시점** SHA로 고정 → **사실(GitHub 동작)**: 이 변경 push 뒤에도 이미 생성된 pending run 1개는 옛 코드로 돈다 → 스모크에서 새 코드 run을 수동 dispatch해 pending을 교체.
- G6 GAS 웹앱 1회 실행 상한 6분 → **사실(Apps Script 할당량 문서)**. 따라서 400초 넘는 응답은 정상이 아님.
- G7 `if: always()` step은 앞 step 실패·run 취소 시에도 실행 → **사실(Actions 문서)**. 러너 유실 시에는 실행 안 됨(11/11 실측) — 그래서 사전 예약이 주경로, 끝 step은 보조.

## 2. 과거 부류 (errors.md)
- 6/10 daisy-chain: `push|tail` 파이프가 종료 코드를 가림 → dispatch 성공 판정은 파이프 없이 `if gh ...; then`.
- 6/10 "고빈도 cron일수록 통째 드롭" → 장중 재시드를 cron에 더 기대지 않음(원안 ③ 보류 사유).
- 10/4·10/5 러너 일시 네트워크로 gh 1회 실패 → 사전 예약은 성공할 때까지 **매 poke마다 재시도**(약 23회 기회).
- 10/4 "실행 시점 시계" 함정 → run 생성 시각(createdAt)이 시작보다 ~115분 앞당겨짐. watchdog은 completed run을 **createdAt의 KST 날짜**로 묶음(`watchdog_check.sh` ②) → 장중 poke(09:00~15:40)를 담는 run은 같은 날 05시~13시대에 생성되므로 날짜가 바뀌지 않음. 날짜 경계를 넘는 run은 자정 전후 생성분뿐이고, 그 poke는 전부 장외라 발송·휴장 판정에 영향 없음. (cron pending run이 이미 같은 방식으로 생성과 시작이 벌어져 있었음 — 42627114291 85분)
- 10/26 OAuth 403 → watchdog ⑥이 HTTP≠200 ≥6건이면 🔴. max-time이 정상 응답을 끊으면 HTTP=000이 쌓여 오탐 → 400초로 정함(실측 최대 64초의 6배).
- 6/10 이름공간 상호작용 교훈 → 같은 concurrency 그룹을 cron 백업·수동 dispatch·사전 예약이 공유. 셋 중 무엇이 pending이 돼도 같은 job이라 체인은 한 줄로 유지(G1).

## 3. 추론 가능 vs 실환경 전용
- 머리로 거름:
  - 폭주 방지: 사전 예약을 시작 5분 뒤로 미룸 → run이 매번 즉시 죽어도 순환은 최소 5분 간격(시간당 ≤12회). 끝 step 보조 dispatch도 "5분 미만 생존"이면 하지 않음(현행 secret 미설정 soft-skip이 즉시 재dispatch로 무한 순환하던 잠복 결함도 같이 닫힘).
  - 중복 dispatch 무해: gh가 생성 후 비정상 종료해 재시도가 두 번 만들어도 G1로 pending 1개로 수렴.
  - 동시 실행 0: concurrency가 보장. GAS 18분 dedup이 혹시 모를 겹침도 흡수.
  - 수동 정지: `gh workflow disable`만으로는 이미 생성된 pending 1개가 남아 한 번 더 돈다(그 run의 사전 예약은 실패 → 끝에 🔴 알림 1회). 완전 정지 = disable + pending·실행 중 run 취소 → 헤더 주석에 명시.
  - 끊김 알림의 의미 변경: "후속 run을 끝내 예약하지 못함"일 때만 발송(`steps.next.outcome == 'failure'`). poke step이 예약 뒤에 실패해도 체인은 이어지므로 알림 안 함.
- 실환경에서만 (→ 스모크로):
  - 취소된 run 뒤에 pending이 실제로 즉시 시작하는가(G3 취소판) → S3
  - 새 코드 run이 5분 뒤 실제로 pending 후속을 만드는가 → S2
  - 러너 유실 판정 지연(11/11 45분)이 다음에도 비슷한가 → 재발 시 run 기록으로 측정(잔여 위험 R3)

## 4. 상대 시스템에서 보이는 것
- GitHub: dispatch API 호출 횟수는 run당 1회(지금과 같음, 실패 시 poke마다 1회 재시도). GAS 웹앱: poke 빈도·내용 변화 없음. 해당 없음에 가까움.

## 5. 검증 방법
- 자동(로컬): ruby YAML 파싱 → 파싱 성공·step 3개 / step `run` 블록 추출 후 `bash -n` → 구문 오류 0.
- 스모크(실환경, 오늘):
  - S1 push 뒤 수동 dispatch → 옛 코드 cron pending(42961789641)이 cancelled로 교체되고 새 run이 pending.
  - S2 현재 run(42960192907, 옛 코드)이 06:31Z(15:31 KST)쯤 끝나면 새 run 시작 → 시작 약 5분 뒤 로그에 `후속 체인 run 사전 예약` + `gh run list`에 pending workflow_dispatch 1개.
  - S3 장중 푸시가 끝난 15:40 KST 이후 새 run을 수동 취소 → pending 후속이 1분 안에 in_progress, 취소된 run의 Alert step은 skipped(끊김 알림 없음).
- 잔여 위험(이 변경으로 못 막는 것):
  - R1 run 시작 후 5분 안에 러너 유실 → 후속 없음 → cron 백업에 의존. 120분 중 5분, 약 4%.
  - R2 GitHub Actions 전체 장애.
  - R3 러너 유실 판정 지연(11/11 실측 45분) 동안 공백 → 장중이면 푸시 약 2회 누락.
  - → 재발하면 GitHub 밖의 독립 시계(GAS 시간 트리거 또는 Cloudflare cron)가 "마지막 poke 30분 경과" 알림을 보내도록. pending에 관찰 항목(⏰2026-11-25)으로 남김.

→ 게이트: **통과** — G3(취소 후 이어받음)은 [검증 필요]이나 S3 스모크로 오늘 확인, 실패해도 현행보다 나빠지지 않음(끝 step 보조 dispatch 유지).
