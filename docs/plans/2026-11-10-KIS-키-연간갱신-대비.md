내년(그리고 매년) KIS 키 갱신에서:
1. **만료 전에** 텔레그램으로 안다.

5. 실행 경로마다 다른 키·다른 코드가 도는 상황 자체가 생기지 않는다.

## 4. 설계

### A. 🔑 KIS 키 갱신 메뉴 (KIS_API.js + Main.js `onOpen`)
- 🛠️ 유지보수 → **🔑 KIS 키 갱신** → 입력창 3개: ① 새 앱키 (비우면 키 유지·만료일만 변경 — "기간 연장" 대비) ② 새 앱시크릿 ③ 만료일 `YYYY-MM-DD` (빈칸이면 오늘+1년을 제안하고 "KIS 화면 날짜와 같은지" 확인).
- 입력 정리: 앞뒤 공백 제거, 중간 공백·빈값 거부, 날짜 형식·오늘 이후 검사.
- **시험 후 저장 (원자적)**: 새 키로 토큰 발급 → **성공할 때만** 속성 `KIS_APP_KEY`·`KIS_APP_SECRET`·`KIS_KEY_EXPIRES` + 새 토큰·만료·지문 저장, 알림 상태 리셋 → 국내 1종목 현재가 조회로 시세 API 확인 → `updateAllNew` → 결과 창 "✅ 토큰 발급 · 시세 조회 · 전체 업데이트 완료 · 만료일 YYYY-MM-DD (D-N)" + 텔레그램 "🔑 KIS 키 갱신 완료" 1통.
  - 실패: **아무것도 저장 안 함**, KIS 응답 본문 앞부분을 그대로 표시 → 옛 설정 유지.
- 키 읽기 `_kisKeys()`: **속성 우선, 없으면 `SECRET`** (Secret.js는 수정하지 않음). KIS_API.js의 `SECRET.KIS_APP_KEY`·`SECRET.KIS_APP_SECRET` 참조를 전부 이 함수로 교체. `KIS_BASE_URL`은 그대로.

### B. 토큰 캐시 앱키 지문 (`getAccessToken`)
- 저장 시 `KIS_TOKEN_KEYFP` = SHA-256(앱키) 앞 12자. 재사용 조건 = 만료 전 **그리고** 지문 일치. 누가 어떤 경로로 키를 바꿔도 다음 호출에서 자동 재발급.

### C. 만료 사전 알림 (`scheduledDailyUpdate` 맨 앞, try/catch로 업데이트와 분리)
- 남은 일수가 **30·14·7·3·1·0** 문턱을 처음 넘을 때 텔레그램 1통, 만료 후엔 매일. `KIS_KEY_ALERT_LAST`(마지막으로 보낸 문턱)로 중복 방지 — 트리거가 하루 빠져도 다음 날 보냄. 메시지에 할 일 3줄 포함.
- **꼬리말 (v2)**: D-14부터 장중 푸시(`_tgFormatPnL`) 맨 아래 "🔑 KIS 키 만료 D-N — 🛠️ 유지보수 → 🔑 KIS 키 갱신" 한 줄. 하루 수십 번 보는 메시지라 놓칠 수 없음.
- 🔍 진단에 `kisKeyExpires`·`kisKeyDaysLeft`·`kisKeySource`(property/secret) 추가.

### D. 토큰 발급 실패 즉시 알림 (`getAccessToken` 실패 분기)
- KIS가 오류로 응답하면 **하루 1통** "🔴 KIS 토큰 발급 실패 — <응답 요약>. 키 만료면 🛠️ 유지보수 → 🔑 KIS 키 갱신". 속성 `KIS_TOKEN_FAIL_ALERT_DATE`로 중복 방지(HEAD·웹앱 경로 공유).

### E. 앱 404 안내 (v2: web·desk 지금, iOS는 다음 빌드 때)
- web `gasApi.ts` · web-desk `gasApi.ts`: 404 + "Requested entity was not found" → "GAS 대상 못 찾음 — 소유자 계정으로 GAS 에디터에서 한 번 저장하세요". iOS `ScriptAPIService.swift`는 다음 Xcode 빌드에 묶음.

### F. 웹앱 배포 동기화 (v2 신규 — `push_safe.py`)
- PUT 성공 후 **내용이 바뀌었으면** 새 버전 생성 → 웹앱 배포 3개를 그 버전으로 교체. 내용 동일하면 아무것도 안 함. `--no-deploy`로 끌 수 있음.
- 버전 한도 200(Google 2024 적용) — 현재 33. GAS push 실측: 5월 27회·6월 12·7월 14·8월 2·9~11월 0 → 수년 여유. **180개 이상이면 경고** + 정리 방법(프로젝트 기록 화면에서 미배포 버전 삭제) 출력.
- 롤백: 직전 버전 번호로 배포 3개를 되돌리는 `--rollback`.
- 효과: "최신 코드 = 모든 경로에서 실행되는 코드"가 상시 성립 → §0 같은 상황이 코드·키 어디서도 재발 불가.

### G. 운영 배포 권한 (v2 — 사용자 결정)
- 권한 분류기가 push_safe를 "운영 배포"로 막음 → F·긴급 재배포·내년 대응이 매번 막힘. 사용자가 원하면 `python3 apps-script-v2/push_safe.py` 실행 허용 규칙을 설정에 추가(사용자 요청 시 Claude가 추가). 거절 시 배포 단계마다 사용자 허가 메시지로 진행.

### H. (선택) Life OS 연 1회 반복 등록
- "KIS 앱키 갱신" 연 1회 반복(영역 재무) — FD5to6 코드·텔레그램과 독립된 두 번째 알림. 만료일 확정 후 미리보기 확인받고 등록.

### 범위 밖 (의도적 제외)
- KIS가 토큰을 중간 폐기하는 경우(만료 전 무효) 자동 재시도 — 드묾, D 알림으로 가시화만.
- watchdog 변경 — 현행대로 최후 안전망.

## 9. 2026-11-13 추가 설계 — 🔑 메뉴(축소판) · 날짜별 속성 정리 (`/design-check`)

> 배경: 배포 전 재검증에서 두 가지 발견. ① 이메일 일일 카운터가 날짜별 속성(`email_count_<날짜>`)으로 쌓이고 지워지지 않음(6/20 도입, 리포트 발송일 약 115일 → 속성 100개 이상 **[추정 — 원격 속성 개수는 직접 못 셈]**). 공식 문서상 속성 화면의 수동 추가는 50개까지라 리허설의 "속성 두 칸 추가"가 막힐 수 있음 **[미확인 — 50개 초과 시 화면 동작은 문서에 없음. 11/10엔 같은 화면에서 두 줄 삭제는 됐음]**. ② 같은 키를 넣는 리허설은 지문이 같아 토큰을 새로 받지 않음 → 시크릿 칸 오타를 못 잡음(스텁 시험으로 확인).
> 사용자 결정(11/13 "둘 다 진행해"): §4-A 메뉴를 **축소판**으로 지금 넣고, 날짜별 속성 누적을 정리한다. 리허설은 속성 화면 대신 메뉴로.

### 범위
- **`kisRotateKey()`** (KIS_API.js, 메뉴 `🛠️ 유지보수 → 🔑 KIS 키 교체`): 입력창 2개(앱키·앱시크릿) → 공백·줄바꿈 제거 → 그 값으로 토큰 발급 요청 → **성공할 때만** `KIS_APP_KEY`·`KIS_APP_SECRET`·토큰·만료·지문을 `setProperties` 한 번으로 저장. 실패·취소·빈값이면 아무것도 안 바뀜. §4-A의 만료일 입력·시세 시험·전체 업데이트 연쇄·텔레그램 통지는 계속 보류(완료 창이 "🔄 전체 업데이트"를 안내).
- **`_kisRequestToken(key, secret)`**: `getAccessToken`의 요청부를 그대로 떼어 메뉴와 공유. 요청 형태(주소·헤더·본문)·실패 문구 불변.
- **이메일 일일 카운터**: `email_count_<날짜>` → 한 칸 `email_count` = `날짜|횟수`. **상태(덮어쓰기)** — 하루 상한 판정용이며 발송 이력의 원본은 Gmail 보낸편지함·Actions 로그라 이력을 잃지 않음. 옛 날짜별 키는 발송 성공 뒤 실행당 최대 60개씩 삭제(`_emailCountCleanup`), 응답에 `cleaned` 개수.
- **🔍 진단** `propCount`(속성 개수, 이름·값 없음).

### 9-1. 외부 동작 가정
- `Ui.prompt`가 현재 스코프로 동작 → 같은 `Ui` 클래스의 `alert`가 🔍 진단에서 현재 동작. 레퍼런스에 `prompt`의 별도 스코프 표기 없음 **[리허설에서 최종 확인]**. 안 되더라도 메뉴 실행만 실패 — manifest 스코프는 그대로라 앱·트리거·웹앱에는 영향 없음.
- 속성 쓰기는 프로젝트 저장 기록을 바꾸지 않음 → §5-1 사실(11/10 속성 삭제 후 modifiedTime 유지). 메뉴는 편집기 저장이 아니므로 앱 404 경로와 무관.
- `setProperties(obj)` 한 번 호출 = 다섯 값이 함께 반영(중간 상태 없음) → `getAccessToken`이 이미 같은 방식으로 세 값을 저장 중.
- `getKeys()`·`deleteProperty()`는 지정한 키만 다룸 → 정리는 정규식 `^email_count_\d{4}-\d{2}-\d{2}$`에 맞는 키만. `deleteAllProperties`·`setProperties(…, true)`는 쓰지 않음(동시 쓰기 유실 위험).
- 속성 화면 수동 추가 50개 한도 → **사실**(Properties Service 가이드). 초과 시 편집·삭제 가능 여부 → **[미확인]** — 메뉴가 화면에 의존하지 않으므로 설계 무관.
- KIS 토큰 발급 1분 1회 제한·실패 응답 형식 → **[실환경 전용]**(§5-1 그대로) — 형식을 가정하지 않고 본문 앞부분을 표시, 입력값이 되돌아오면 가림.
- 이메일 응답 JSON에 `cleaned` 추가 → 워크플로는 응답을 로그에 찍기만 함(`market-report.yml` 세 곳, 해석 없음) → 영향 없음. 값은 개수뿐.
