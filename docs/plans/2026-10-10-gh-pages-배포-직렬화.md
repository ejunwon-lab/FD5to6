# 설계 노트 — gh-pages 배포 직렬화 (2026-10-10)

문제: `deploy-web.yml`·`deploy-web-desk.yml`이 같은 `gh-pages` 브랜치에 push(`keep_files: true`). 한 커밋이 양쪽을 건드리면 동시 실행 → 늦은 push가 non-fast-forward 거부(d9b2781 실측, errors.md 2026-10-10).

변경: 두 워크플로에 공통 `concurrency: {group: gh-pages, cancel-in-progress: false}`.

1. 외부 동작 가정: GitHub concurrency 그룹은 워크플로 간에도 공유된다(그룹명이 같으면 repo 단위로 직렬화) → GitHub 문서 "concurrency group은 workflow 간 공유 가능". pending은 최신 1개만 유지·이전 pending 취소 → 최신 커밋 배포라 무해. `cancel-in-progress: false`라 실행 중 run은 보호.
2. 과거 부류: 6/8 "안전망 2회 레이스"·7/23 web 배포 7일 침묵 실패 — 배포 run 결과 확인 습관. 이번 변경은 run을 줄 세울 뿐 성공·실패 판정 무관.
3. 머리로 거름: 그룹 공유·취소 규칙. 실환경: 실제 직렬화는 양쪽 동시 트리거 때만 관찰 가능 → 이번 커밋은 워크플로 파일 2개가 각자 자기 트리거(`paths`)에 걸려 **동시 발화** → 바로 실측.
4. 외부 시스템 부하: 없음.
5. 검증: push 후 두 run 중 하나가 queued/pending으로 대기했다가 순차 success. 라이브 사이트 200.
