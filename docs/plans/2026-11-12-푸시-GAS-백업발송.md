- 날짜: 2026-11-12 · 대상: `apps-script-v2/Telegram.js`(신규 `tgChainFallback`·`_tgFallbackDue`) · `apps-script-v2/Main.js`(`scheduledHourlyUpdate` 앞머리 호출) — 트리거 진입점 변경 → `/design-check` 대상
- 배경: 11/12 05:40 KST GitHub 장애로 사전 예약된 후속 run이 러너 배정 실패(시작 전 failure) → 체인 끊김, 장중 cron 백업 09:00~14:16 약 16틱 전부 미발화 → 오전 0통. 11/11 사전 예약(f72c552)은 "돌던 run이 죽는 경우"만 막는다. 체인·cron이 둘 다 GitHub 안에 있어 함께 멈춘다.

## 안
GAS에는 GitHub과 무관하게 30분마다 도는 시간 트리거(`scheduledHourlyUpdate`, HEAD 코드)가 이미 있다(11/12 장애 중에도 08:56~13:56 매 틱 발화 — 로그 실측). 그 앞머리에서:

- 거래일 · 09:10~16:00 · **직전 발송(`tg_lastPushEpoch`) 후 27분 이상** → GitHub 신호가 끊긴 것으로 보고 `tgPushPnL()`을 직접 호출(전체 갱신 + 발송). 발송에 성공하면 그날 1회만 "GitHub 신호 끊김 — GAS가 대신 보냄" 알림.
- 그 외에는 아무것도 안 함.

신호 판정에 "poke 수신 시각"이 아니라 **직전 발송 시각**을 쓰는 이유: ① 기존 속성이라 웹앱 고정 배포(v34) 재배포가 필요 없다(HEAD push만 — 트리거는 HEAD 실행) ② 목적이 "푸시가 안 옴"의 감지이므로 더 직접적 ③ poke는 오는데 웹앱 쪽이 고장 난 경우도 덮는다.

체인 재시작은 하지 않는다(GitHub 토큰 필요 — 2안, 보류). 복구는 알림을 본 뒤 수동 `gh workflow run` 또는 cron 재시드.

## 1. 외부 동작 가정
- A1 시간 트리거는 HEAD 코드를 실행 → **사실**(errors.md 388·397행, 7/17 배포 기록 "HEAD — 메뉴/트리거 즉시 반영"). 웹앱 버전 재배포 불필요.
- A2 `scheduledHourlyUpdate` 트리거는 30분 간격, 오프셋 :26/:56, 지터 ±6초 → **사실(11/12 로그 7틱: 01:56:29Z~04:56:30Z)**.
- A3 `tgPushPnL`은 트리거 컨텍스트에서 동작 → **사실**(6/5까지 트리거 핸들러였음, errors.md 230행). HEAD의 `updateAllNew`·KIS 키도 정상(11/12 매 틱 "42개 종목 업데이트").
- A4 정상 체인의 발송 간격 상한: dedup 18분 + poke 5분 간격 → 통상 20~22분, poke 1회 실패·`skip-lock` 시 약 25분 → **사실(11/11 로그: 12:01→12:22 등)**. 따라서 틱 시점 경과 27분 이상은 poke 2회 연속 실패 이상에서만 — 그 경우 백업 발송은 오히려 바람직.
- A5 GAS 시간 트리거 자체가 best-effort(6/5 3.5시간 부재) → **사실**. 그래서 주경로가 아니라 **백업**으로만 쓴다. GitHub 장애와 GAS 트리거 누락이 겹치면 못 막음(잔여 위험).
- A6 배포 계정 = 스크립트 소유자 → **사실(11/12 실측: clasp 토큰 계정 ∈ Drive owners, 마지막 저장자도 소유자)** — 11/10 "소유자 아닌 계정 저장 → 앱 404" 부류 회피.

## 3. 추론 가능 vs 실환경 전용
- 머리로 거름:
  - 중복 없음: 백업 발송이 `tg_lastPushEpoch` 슬롯을 선점 → 되살아난 체인의 poke는 18분간 `skip-dedup`. 반대로 정상 체인이면 틱 시점 경과 < 27분이라 호출 자체가 없음.
  - 백업 모드 카덴스: 틱 30분 간격, 자기 발송 후 다음 틱 경과 ≈ 29.9분 ≥ 27 → **30분마다 1통**(평소 20분보다 듬성). 09:26 첫 통 ~ 15:56 마지막 통, 하루 14통.
  - 갱신 중복 회피: 백업이 `sent`면 `scheduledHourlyUpdate`는 바로 return(방금 `updateAllNew` 수행).
  - 격리: `tgChainFallback` 전체 try/catch — 실패해도 기존 매시 갱신은 그대로 진행.
  - ㄱㄱ 수동 발송도 슬롯을 갱신 → 그 뒤 27분은 백업 안 나감(정상).
  - watchdog 영향: 백업 발송은 GitHub 로그의 `sent`에 안 잡힘 → 그날 밤 "발송 < 10건" 🔴 → 체인 문제를 그대로 드러냄(의도).
  - 저장소: 신규 속성 `tg_chainFallbackAlertDate`(yyyy-MM-dd) = **상태**(덮어쓰기, 하루 1회 알림 dedup용). **이력**은 Cloud Logging의 `tgChainFallback:` 줄(조회 가능·30일 보존)로 충분 — 통계가 필요해지면 watchdog가 집계.
- 실환경에서만:
  - 배포 후 실제 틱에서 새 코드가 도는가 → 다음 틱 로그의 `tgChainFallback:` 줄.
  - 발송 경로 실동작(체인을 일부러 끊고 27분) → 장중에만 가능. 11/12는 장 마감 후라 불가 → 아래 5의 "실전 훈련" 또는 다음 실제 장애 때 로그로 확인.
